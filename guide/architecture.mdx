ChefOS exposes product capabilities through stable API domains. You only need the public API model, credentials, and the location scope for the data you are working with.

## Request flow

| Step | What your integration does |
|---|---|
| 1 | Send a request to the ChefOS API base URL for the correct environment |
| 2 | Include `Authorization: Bearer <token>` |
| 3 | Include a location header for location-scoped data |
| 4 | Use returned ChefOS IDs for future reads, updates, and reconciliation |
| 5 | Handle standard HTTP errors and retry only idempotent requests |

## API domains

| Domain | Examples |
|---|---|
| Sales | POS imports, daily summaries, item performance, revenue reporting |
| Scheduling | Employees, shifts, availability, time off, open shifts, shift trades |
| Inventory | Items, counts, recipes, purchase orders, waste, vendor data |
| Messaging | Conversations, channels, participants, notification preferences |
| Employee self-service | Mobile schedule views, time-off requests, shift claims, push registration |
| Assistant | Permission-aware navigation, reports, notification control, scheduled summaries |

## Data scoping

ChefOS data is scoped by organization and, for most operational data, by location. A token can only access the organizations, locations, and permissions granted to it.

## Integration design guidance

- Treat ChefOS IDs as stable references.
- Prefer incremental syncs once the first import is complete.
- Keep write operations narrow and explicit.
- Use read scopes for dashboards and reporting-only workflows.
- Use location headers consistently so reports and updates land in the right store.
