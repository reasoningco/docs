title: "RBAC & Permissions"
description: "Understand role-based access control and permission scoping in ChefOS."
---

ChefOS uses a **deny-by-default** role-based access control system enforced on every authenticated API request.

## Roles

| Role | Description |
|---|---|
| `admin` | Full access to everything &mdash; no permission checks |
| `manager` | Access determined by `section_grants` table |
| `employee` | Access determined by `section_grants` table |

## Permission Format

Permissions follow the pattern `module.section.action`:

```
inventory.items.read
scheduling.shifts.write
sales.analytics.read
chat.messaging.read
```

Wildcard matching is supported:
- `inventory.*.read` &mdash; grants all read access within inventory

## Database Tables

| Table | Purpose |
|---|---|
| `org_membership` | User -> tenant mapping, role level, active status |
| `section_grants` | `(user_id, tenant_id, module, section, access, location_scope)` |
| `user_location_grants` | Location restrictions per user |

## Deny-by-Default

Every authenticated route **must** declare an `authz` config block. Routes without it return `403`:

```typescript
// This route requires inventory.items.read permission
app.get("/items", {
  config: {
    authz: { permission: "inventory.items.read", locationScoped: true }
  }
}, handler);

// Public route &mdash; explicitly opted out
app.get("/health", {
  config: { authz: { public: true } }
}, handler);
```

## Permission Checks

The frontend mirrors backend permission logic in `usePermissions()`:

```typescript
const { hasPermission, hasExplicitGrant, canOpenApp, isAdmin } = usePermissionsContext();

// Check if user can access a module
if (canOpenApp("inventory")) { /* show inventory sidebar item */ }

// Check specific permission
if (hasPermission("scheduling.shifts.write")) { /* show edit button */ }
```

### `hasPermission` vs `hasExplicitGrant`

| Method | Use For |
|---|---|
| `hasPermission` | API-level guards &mdash; includes implicit reference-data grants |
| `hasExplicitGrant` | UI visibility &mdash; only explicit `section_grants` rows |

## Deactivated Users

`is_active` is checked on every request in `resolveAuthContext()`. Deactivated users are immediately blocked with no cached permissions.

## Location Scoping

For location-scoped routes, the `X-Location-Id` header is validated against `user_location_grants`. Non-admin users cannot access locations they haven't been granted.

```
X-Location-Id: loc_abc123
```

Location scope is either `assigned_only` (default) or `all_locations` per permission grant.
